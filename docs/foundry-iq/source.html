07 / Customer acceptance

The path to complete
customer acceptance

For each question: what works today, what must change, and the evidence required to close it. The actions below are proposed work, not capabilities already validated.

Define 100% before measuring it.

Agree the source revisions, required equipment rows and fields, handling of blanks/placeholders, workbook template and authoritative answers. Complete acceptance means every required benchmark check passes. An unresolved value stays a failed or open check, not an invented answer. This is not a guarantee of perfect performance on unseen documents.

Customer questionCurrent status and evidenceSolution to reach complete acceptanceProof / exit criterion
1. Build a KB and connect an agentDemonstrated

KBs and GPT-5.4 agents exist. The Excel agent completed live retrieval followed by file generation.

  1. Freeze a manifest of files, hashes, revisions and source membership; keep native/scanned MEL runs isolated.
  2. Verify ingestion, filename coverage and vectors. Run agreed questions in fresh conversations, including cross-document and no-result cases.
  1. All three supplied PDFs appear in the intended indexes with no failed documents.
  2. Runtime traces prove the correct KB was queried. Expected facts cite the right source; unsupported requests return insufficient evidence.
2. Every equipment row and fieldKey gap

Ranked retrieval cannot prove completeness. Offline extraction found 35 rows / 630 fields, not independently validated ground truth.

  1. Materialize row/cell records from CU structured analysis or DI Layout, with stable package and subitem identities.
  2. Add a live enumeration tool that reads all matching records, follows pagination and returns source/page coverage. Use IQ for grounding and this tool for full registers; do not preload a dataset into Code Interpreter.
  1. Against the customer-approved register: 100% required-row recall, no extra/duplicate rows and 100% required-field agreement.
  2. Account for every page and subitem; missing records or incomplete pagination fail the gate.
  3. Change a source row, reindex and confirm a fresh agent request reflects it without new data attachments.
3. File and page for each valuePartial

Document references and some chunk page ranges exist. A 2-3 page range is not exact per-cell provenance.

  1. Persist document/revision/hash, physical page, table/row/column, raw text and analyzer-returned polygon or span for every field.
  2. Keep provenance IDs through normalization, retrieval and Excel. Add field-evidence links and comments; retain original values and units alongside conversions.
  1. Every required exported field resolves to the exact source revision and physical page.
  2. Check locations against annotated merged/wrapped cells. Missing metadata stays flagged, never invented.
  3. Required provenance coverage is 100%; unresolved links block acceptance.
4. Difficult engineering-table casesPartial

Dynamic Excel preserves the compressor conflict. The full hard-case scorecard has not been run end to end.

  1. Reconstruct wrapped/merged rows; preserve blank raw subitem tags and explicit parent packages. Name hot/cold sides.
  2. Preserve one-of-two train scope, duty/standby, common equipment, VTA/FV/HOLD/AMB, blanks, signs and unit exceptions. Route ambiguous OCR to review.
  1. Pass annotated tests for every edge case on native and scanned inputs, through retrieval and final Excel.
  2. Verify package subitems, paired temperatures, standby power, minus signs and the receiver's mm note.
  3. Keep 4,920 vs 4,850 kW as a conflict; do not misclassify operating vs design pressure as a conflict.
5. Scanned PDFs and CU / DICU demonstrated

CU OCR/layout ingestion and scanned retrieval work. DI is an alternative, not a deployed component.

  1. Retain CU page/table outputs and processing status for the agreed PDFs.
  2. Where CU misses a required case, compare DI Layout or a custom CU analyzer on the same pages/schema. Review signs, punctuation, units and row boundaries; reprocess failures.
  1. All expected pages processed, with no unexplained omissions.
  2. Score native/scanned runs separately against approved values; all critical benchmark cells are correct after documented review.
  3. Retain analyzer versions, raw outputs, errors and rerun evidence.
6. Customer Excel template and scoringDynamic Excel works

Results, Evidence and Review sheets are generated live. The actual template and authoritative answers are not yet supplied.

  1. Agree template mapping, row IDs, units, required cells, tolerances and placeholder handling.
  2. Populate the blank template from live tool results while preserving formatting, formulas and validations.
  3. Use an independent deterministic scorer for row, field and provenance coverage; fix mismatches and rerun.
  1. Workbook opens in Excel, matches the approved template and has no missing required cells or formula/link errors.
  2. Meet the agreed 100% benchmark targets using pre-agreed tolerances.
  3. Repeat in a fresh conversation and after a source update; retain workbook, gold version, trace and score report.
7. Cost and SharePoint without MCPDesign and approval

Search is Basic / 1 replica / 1 partition. The current agent-to-IQ path uses MCP; SharePoint and the replacement runtime are not implemented.

  1. Build a Sweden Central estimate from current rates and measured page/token/query/session usage, including idle Search, Blob and refresh costs.
  2. Use an approved SharePoint indexer or Graph sync, validating preview acceptability, changes/deletions and ACL propagation.
  3. Replace agent-to-KB MCP with an Entra-authenticated application/function tool calling KB REST retrieval.
  1. Itemized low/expected/high cost scenarios reconcile with trial billing; load tests meet agreed latency/capacity.
  2. Add, update, delete and revoke SharePoint content; changes appear within the agreed refresh window.
  3. Authorized/unauthorized user tests prevent data leakage; runtime/network logs show no MCP calls.

08 / Next decisions

From a working demo
to a measurable engineering workflow

  1. Define the acceptance contract

    Obtain the customer workbook template, authoritative values and row/field completeness rules.

  2. Prove exhaustive coverage

    Use an approved source-enumeration or structured extraction tool when every row is required. Do not equate repeated retrieval with guaranteed completeness.

  3. Validate the hard cases

    Wrapped rows, hot/cold pairs, package subitems, train scope, placeholders, signs and cross-document conflicts.

  4. Choose the approved production transport

    Direct knowledge-base REST retrieval can replace MCP. SharePoint ingestion and per-user authorization are a separate design decision.

Cost model

Search baseline: Basic, 1 search unit, billed while provisioned. Exact regional rates are not quoted here.
