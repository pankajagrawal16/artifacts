      The architecture in one sentence

      Centralise the rules, not every team's runtime.

      Agents run in the environment that suits the team. Governed calls converge on API Management; ownership, observability and security extend across the estate.

      Deployment blueprint

      Four reinforcing layers. Different owners. Not four sequential network hops.

      Guidance, not a deployment tool

      What you provision or activate

      A practical activation sequence

      1. 01

        Agree the operating model

        Assign policy, platform, agent-product, IAM, FinOps and security owners. Define allowed assets, residency boundaries and an acceptance bar.

      2. 02

        Establish connectivity and the central hub

        Choose hub-based or dedicated-spoke placement. Configure routes, firewall, private DNS and private endpoints as required; deploy the gateway landing zone.

      3. 03

        Curate supply, then grant demand

        Onboard model capacity with backend contracts. Publish reusable MCP/A2A assets where needed (preview). Create access contracts per business unit, use case and environment.

      4. 04

        Connect an execution spoke

        Deploy or onboard a Foundry, Container Apps, AKS or other supported runtime. Point the relevant model and tool connections at APIM. Configure consumer and backend identities separately.

      5. 05

        Activate cross-cutting trust in parallel

        Register accountable agent identities and owners. Configure Agent 365, Defender, Purview and Entra controls for the chosen agent type; check licensing and feature support.

      6. 06

        Prove the controls before scaling

        Test denied access, quotas, safety, backend failure and trace correlation. Validate tool/data permissions, human approvals, sensitive-log handling and per-contract usage attribution.

      Policy as code

      Three contracts, three different questions

      Two supported network patterns

      A governance hub is a role, not necessarily the network hub.

      A dedicated Citadel spoke is reached through the enterprise hub firewall. A hub-based Citadel gateway is reached directly from peered agent spokes. VNet peering is not transitive; other-spoke backend routing still needs explicit design.

      Private endpoints and DNS secure supported service endpoints. They do not automatically make every external tool, SaaS agent or provider private.

      Local freedom. Global rules.

      Make the next agent easier to govern,
      not harder to approve.

      Citadel separates platform responsibilities from product responsibilities. Teams keep their runtime choices, while the enterprise gets reusable access, capacity, identity and evidence controls.

      As the estate growsDirect, per-team integrationsA shared Citadel approach

      Policy & access

      Every application implements its own keys, permissions and guardrails.

      Contract-scoped access and reusable gateway policies create a consistent enforcement point.

      Capacity & resilience

      Teams compete for quota and build their own retry or fallback logic.

      Per-consumer limits protect shared capacity; configured pools and circuit breakers handle approved failover.

      Ownership & cost

      Unclear agent owners and fragmented usage make accountability difficult.

      Agent identity and lifecycle ownership complement per-contract usage for showback and chargeback.

      Developer experience

      Each product team repeats infrastructure and integration decisions.

      Repeatable execution spokes and discoverable approved assets reduce undifferentiated setup work.

      Evidence & operations

      Request-level logs, agent reasoning traces and security signals live in silos.

      Gateway diagnostics, instrumented agent traces and security tooling provide complementary operational views.

      01

      For the platform team

      Operate a shared gateway and approved capacity instead of maintaining a bespoke integration for every app.

      Useful evidence

      Contract coverage, backend errors, quota rejections and successful recovery tests.

      02

      For builders & business teams

      Build agents close to the use case, reuse approved tools and models, and retain responsibility for product quality.

      Useful evidence

      Time to onboard a use case, evaluation results, tool correctness and human-approval coverage.

      03

      For IAM, security & FinOps

      Know who owns an agent, what it may access, which team consumed capacity and where signals need investigation.

      Useful evidence

      Owned identities, least-privilege checks, retained audit records and reconciled usage attribution.

      A gateway is not a guarantee of trust.

      The hub is shared infrastructure to size, secure and operate. Policies add processing and can add latency; fallback needs real capacity. Product teams still own agent evaluations, tool approval and data permissions. Prompt/body logging needs explicit data-governance decisions. SaaS routing, Agent 365 coverage and preview integrations vary by agent type and feature availability. Compliance requires evidence and organisational controls, not just deployment.

      How to read this visualisation

      • The canvas is an educational logical architecture, not a complete resource topology or a deployable design. Packet speed is for teaching, not measured performance.
      • L1–L4 are complementary responsibility layers. Agent 365, Entra, Defender and Purview are not four serial proxies in the request path.
      • Registry discovery and contract deployment are control-plane concerns. The agent's runtime model/tool/A2A calls use gateway endpoints only when explicitly configured and supported.
      • The map expands the enterprise-firewall hop for agent ingress in dedicated-spoke mode. Backend subnet routing, DNS resolution, moderation-service calls and token issuance are summarised rather than fully drawn.
      • Gateway diagnostics are not a complete agent reasoning trace. Instrument the agent/runtime and tools for end-to-end spans. Prompt/response body capture is optional and must be governed.
      • No live Azure calls, credentials, tenant identifiers, presentation media or customer-specific resources are included.

      Preview and support boundaries worth checking

      Publish contracts and Foundry-hosted A2A publishing: marked preview in the accelerator. Publishing an endpoint does not grant access; access contracts are separate.

      Foundry portal MCP gateway integration: Microsoft Learn currently limits automatic routing to eligible new MCP tools created after gateway connection, excluding managed OAuth and certain other tool types. Existing tools are not automatically rerouted. Gateway logs do not provide tool-level traces.

      Networking, authentication and service tiers: choose supported APIM capabilities and auth modes for the actual runtime and backend. Do not assume SaaS-internal traffic or all tool integrations can be intercepted.
