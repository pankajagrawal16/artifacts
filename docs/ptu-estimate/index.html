Capacity and cost framing

Design for the academic peak without paying for it every quiet day.

The service is a shared AI platform, not one flat workload. The decision is therefore not simply PayGo versus PTU: it is which model and content-policy lanes warrant a stable provisioned baseline, and which should remain on token billing with controlled spillover.

Recommendation frame

Use provisioned capacity as a measured baseline, then let Standard absorb the migration tail and exam bursts.

This is a decision framework, not a commitment recommendation. It avoids treating the 24 deployments as one average workload and preserves model choice while the portfolio evolves.

Recommended operating pattern

Segment the portfolio by observed demand. Assign stable, latency-sensitive lanes a measured PTU baseline. Keep low-volume, newly released, retiring, or highly seasonal lanes on Standard. Configure approved spillover from provisioned Azure OpenAI deployments to Standard for exceptional bursts.

  • Size every distinct model and policy lane independently. Do not divide the 42B-token total evenly across 24 deployments.
  • Separate deployment operations from reservation billing. A reservation can cover matching PTU deployments across scope; it is not purchased for one model.
  • Prove baseline demand first. Use hourly and per-minute telemetry plus a production-shaped benchmark before reserving a long-term PTU quantity.

Global Provisioned

Use this option only if global data routing is accepted. It offers the broadest placement flexibility while retaining fixed provisioned throughput after deployment.

  • Operational advantage: a Global reservation can cover matching Global PTU deployments across regions within its scope.
  • Use when: availability and centralized reservation coverage matter more than a geographic routing boundary.
  • Verify: model/version availability, capacity at deployment time, data policy, and scope across the 10 subscriptions.

Global provisioned reservations and Data Zone provisioned reservations are different products; one does not cover the other.

EU Data Zone Provisioned

Use this option when European data-zone routing is required or preferred. It preserves a zone-level routing boundary while avoiding a single-region-only pattern.

  • Operational advantage: dedicated capacity and predictable latency within the eligible data zone.
  • Use when: the data boundary is a governing decision and candidate models support Data Zone provisioned deployments.
  • Verify: model/version availability, selected region capacity, per-subscription quota, and region matching for reservation coverage.

Data Zone PTU quota and reservation coverage still require matching deployment type and region. Quota is not a capacity guarantee.

Evidence boundary

What can be concluded now, and what must arrive before an actual price or PTU commitment.

The 42B-token total validates that a provisioned option is worth analyzing. It does not disclose the per-minute peak, request shape, cache behavior, or model mix required to estimate capacity.

Known from the brief

  • Material demand: 42B tokens YTD and an approximately 60B annual run rate.
  • High seasonality: peak day is about 10 times the quietest day; weekend and holiday demand is low.
  • Portfolio behavior: multiple models and content-policy lanes run concurrently during gradual migrations.

Required for a signed-off estimate

  • Per model/version and policy lane: peak RPM, input tokens per call, output tokens per call, and cache rate, at one-minute granularity for exam-week peaks.
  • Deployment facts: exact model versions, candidate region, Global versus Data Zone choice, PTU quota, and live capacity availability.
  • Commercial inputs: billing currency, hourly or reservation PTU price, Standard input/output token prices, and eligible reservation scope.

Do not use an average of total tokens or an even division across 24 lanes for PTU sizing. A single large-output model or exam-hour request pattern can dominate the normalized PTU demand.

PTU estimate

Size one model and content-policy lane at a time.

The worksheet implements Microsoft's published manual formula for the GPT-4o through GPT-5.x-style sizing method. It deliberately begins empty: the values must come from Fjordlight's extracted telemetry and the exact model/version table in Microsoft Learn.

Lane inputs

Choose a documented model profile, select the deployment type, then enter measured peak traffic. Customer demand is never guessed.

1. Choose model and deployment

Choose a documented profile to autofill model-specific PTU constants, or use a custom model and open advanced settings.

GPT-4o through GPT-5.x formula Use for GPT-4o, GPT-4.1, and GPT-5 profiles

This is the normal worksheet path. It asks: at your busiest minute, how much does the model read and how much does it write?

  1. Count peak requests, input tokens, and output tokens.
  2. Reduce the input portion by the measured cache rate.
  3. Apply the profile's output weighting, then divide by that profile's capacity per PTU.
normalized TPM = input TPM x (1 - cache rate) + output weight x output TPM
Example using GPT-5: 60 requests/minute x 2,000 input tokens creates 120,000 input TPM. With 500 output tokens per request, output TPM is 30,000. GPT-5 applies an output weight of 8, so the normalized demand is 360,000 TPM. The workbook then rounds this to the supported PTU increment.
GPT-6 normalized-token method Use only for the exact GPT-6 model being deployed

GPT-6 capacity cannot be estimated safely from just one cache percentage and one output multiplier.

  1. Separate new input from input reused from the prompt cache.
  2. Account for cache writes: the first-time work that makes a prompt segment reusable.
  3. Apply the current GPT-6 model's individual weights for input, cached input, cache writes, and output.
Why the worksheet stops here: two GPT-6 workloads with the same total token count can need different capacity when one reuses its cache more often. Use the exact current Microsoft Foundry sizing table or capacity calculator for that model rather than treating it as a GPT-5-style estimate.
2. Enter observed peak traffic

Use peak RPM and request shape from the same workload window. The page does not infer cache behavior from total tokens.

Decision sequence

Turn the workbook into a recommendation in four bounded steps.

01

Classify every lane

List the exact model version, content-policy configuration, migration stage, candidate deployment type, and data-routing requirement.

02

Extract peak shape

Use per-minute exam-period data to capture RPM, input/output tokens, cache rate, and peak duration for every active lane.

03

Size and benchmark

Apply the calculator per lane, verify capacity in Foundry, then benchmark representative traffic and observe provisioned utilization.

04

Commit coverage

Create viable deployments first. Then cover their stable PTU total with matching Global or Data Zone reservation scope, leaving seasonal tails on Standard.
